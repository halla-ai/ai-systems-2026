# 실시간 채팅 기능 런북

## 🎯 Status & Context

우리 서비스는 실시간 채팅 기능을 도입하는 것을 목표로 하고 있습니다. 현재는 웹 기반으로 시작하지만, 서비스 확장을 위해 향후 모바일 지원과 마이크로서비스 아키텍처(MSA)로의 전환을 고려하고 있습니다. 이 문서는 실시간 채팅 기능의 구현과 관련된 현재 상황과 주요 결정 사항을 제공합니다.

## 🏛 Decision

초기의 구현 용이성과 팀의 기술적 숙련도를 고려하여, 실시간 기능 구현에는 Socket.io를 선택했습니다. 또한 '어댑터 패턴'을 적용하여 향후 gRPC로의 마이그레이션 유연성을 확보했습니다. 이를 통해 초기 개발 속도를 높이는 동시에, 필요에 따라 다른 기술로 전환할 수 있는 가능성을 염두에 두었습니다.

* **Socket.io 선택 이유:**
  - 학습 곡선이 낮고 설정이 용이하여 초기 구현의 부담을 줄일 수 있습니다.
  - 현재 팀원들의 기술 스택과 잘 맞아 효율적인 개발이 가능합니다.

* **아키텍처적 유연성:**
  - 어댑터 패턴을 사용하여 차후 gRPC로의 전환을 쉽게 할 수 있도록 설계되었습니다.

## ⚖️ Alternatives & Trade-offs

### 고려했던 대안: gRPC-web

- **장점:**
  - gRPC는 높은 성능과 확장성을 제공하여 장기적인 관점에서 더 유리할 수 있습니다.
  - 특정 비즈니스 로직에 대해 명확한 인터페이스와 강력한 타입 검사를 제공합니다.

- **단점:**
  - 초기 설정의 복잡성 증가
  - 팀원의 기술적 숙련도가 현재 수준에는 부합하지 않을 수 있다는 문제

Socket.io를 선택함으로써 초기 설정과 학습 곡선이 낮아졌지만, 장기적으로는 성능 제약(kv의 확장성 등)이 있을 수 있습니다.

## 💡 Future Roadmap

1. **모바일 지원:**
   - 모바일 앱으로의 확장을 대비하여 웹과 통합된 API 및 통신 프로토콜을 검토해야 합니다.
   - 플랫폼 간 싱크 및 상태 유지에 대한 전략 설계가 필요합니다.

2. **MSA로의 확장:**
   - 서비스가 성장함에 따라 MSA로의 전환이 필수적일 수 있습니다.
   - 각 마이크로서비스 간의 통신을 gRPC 등으로 전환할 시 영향도 분석을 실시해야 합니다.

3. **코드 유지보수 및 발전:**
   - 유지보수 시 어댑터 패턴을 사용한 아키텍처 변경의 용이성을 염두에 두어야 합니다.
   - 주기적인 코드 검토를 통해 변경 사항을 시스템화하고, 확장성을 지속적으로 유지해야 합니다.

이 런북은 팀이 실시간 채팅 기능을 성공적으로 도입하고 발전시켜 나가는 데 중요한 지침서로 기능할 것입니다. 각 단계의 기록과 평가를 통해 서비스의 향후 성장을 도모하시기 바랍니다.
